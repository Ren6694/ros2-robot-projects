# 05 点位控制节点与运动日志

> 包：`src/arm_demo/`
> 三个文件构成一条完整的"任务 → 度量"链路：
> `config/waypoints.yaml`（任务脚本）→ `arm_demo/waypoint_mover.py`（ROS 侧）
> → `arm_demo/motion_log.py`（纯 Python 复算层）。
> 外面再套一个 `scripts/run_waypoint_demo.sh` 负责进程编排，`scripts/compare_motion_runs.py`
> 负责跨运行一致性。

## 0. 这个节点要证明的东西

不是"让机械臂动起来"，而是三件更可验证的事：

1. **规划与执行各自可判定** —— 日志要能区分"规划不出来"和"规划出来了但没执行到位"，
   而不是只给一个总的成功/失败。
2. **误差可复算** —— 判据用的公式（到位误差、跟踪误差、路径长度）全部写在
   不 import ROS 的模块里，仿真早关了也能拿同一份代码把 PASS 重新算一遍。
3. **跨运行可比** —— 同一串点位跑过十六次（十四次 full、十二次进比对，§7），
   哪些量必须逐字相同、哪些量允许波动、波动到什么程度算故障，要有明确答案（§6、§7）。

---

## 1. 接口选型：action 图是抓出来的，不是抄来的

先跑 `bash scripts/probe_moveit_interfaces.sh`，实测本机 `/move_group` 这套栈只有 3 个 action：

```
/move_action                                   moveit_msgs/action/MoveGroup
/execute_trajectory                            moveit_msgs/action/ExecuteTrajectory
/arm6_controller/follow_joint_trajectory       control_msgs/action/FollowJointTrajectory
```

三条互相独立的证据表明**两套 Python wrapper 都用不了**（详细过程见 01 §5）：

| 证据 | 实测 |
|---|---|
| apt 索引（清华镜像 2026-09-13） | `ros-jazzy-moveit-commander` **不存在** |
| `/opt/ros/jazzy/lib/python3.12/site-packages` | 只有 `moveit_configs_utils`、`moveit_msgs`，**没有 `moveit/`** |
| `ros-jazzy-moveit-ros-planning-interface` 2.12.4 | 只发 3 个 C++ `.so`，无 Python 绑定 |

所以节点直接用**消息级接口**（`rclpy` + `moveit_msgs/action/MoveGroup`）。
这不只是退而求其次 —— 消息级把规划/执行拆成两个 action 之后，才能各自计时、各自判失败码，
`MoveGroupCommander` 的 `go()` 一条龙反而看不到这些。代价是要自己拼 `MotionPlanRequest`。

## 2. 请求怎么构造

```python
req = MotionPlanRequest()
req.group_name      = group              # SRDF 里的 "arm" / "gripper"
req.pipeline_id     = "ompl"             # 与 moveit.launch.py 的 planning_pipelines 一致
req.planner_id      = "RRTConnect"       # 留空则用 OMPL 默认；写死才能跨次比较
req.allowed_planning_time  = 5.0
req.num_planning_attempts  = 3
req.max_velocity_scaling_factor      = 0.5   # 对 joint_limits.yaml 的再缩放
req.max_acceleration_scaling_factor  = 0.5

goal = MoveGroup.Goal(
    request=req,
    planning_options=PlanningOptions(plan_only=True),   # ★ 执行是下一步
)
```

目标用**关节空间约束**而不是位姿目标，因为点位表本身就是关节角，走位姿目标要先解 IK，
把"IK 无解"和"规划失败"两件事混在一起。每个关节一条 `JointConstraint`：

```python
JointConstraint(joint_name=name, position=pos,
                tolerance_above=1e-4, tolerance_below=1e-4, weight=1.0)
```

三个容易写错、且写错了不报错的地方：

- **`start_state` 故意留空**。空 = 让 move_group 用它自己规划场景里的当前状态。
  客户端显式塞状态反而危险：本节点缓存的 `/joint_states` 可能已经过期，
  塞进去会出现"起点是 200 ms 前的姿态"，然后 TOTG 要在轨迹开头补一段回头路。
- **`tolerance` 就是精度上限**。§6 会看到实测到位误差稳定在 `0.7~1.0e-4 rad` ——
  正好压在这个 1e-4 上，而不是压在 JTC 的 `goal: 0.003` 上。也就是说
  **本项目的精度由规划侧决定**；想再提高，改这个参数而不是改控制器。
- **`sorted(target.items())`**：字典遍历顺序影响日志可读性，也影响
  `arr_err_per_joint` 的键序；固定排序后两次运行的 JSONL 才能直接 `diff`。

### 2.1 错误码落在哪一段

`moveit_msgs` 2.6.0 的 `MoveItErrorCodes`，本项目的实测路径上会遇到的：

| 码 | 名 | 出现在 | 本项目里的真实成因 |
|---|---|---|---|
| `1` | SUCCESS | 两段 | — |
| `-1` | PLANNING_FAILED | plan | 点位表超出可达域 / OMPL 时间不够 |
| `-4` | CONTROL_FAILED | **exec** | 两种：DDS 发现竞态、JTC 真拒绝轨迹（§8） |
| `-6` | TIMED_OUT | 两段 | 客户端 `spin_until_future_complete` 先到点，节点自己记的码 |
| `-10` | INVALID_GOAL | plan | 目标超 URDF `<limit>`、轨迹时间非法 |
| `-12` | GOAL_IN_COLLISION | plan | 点位自碰撞（碰撞矩阵见 04 §3） |

`-6` 是**客户端造出来的**码：action 层面并没有失败，是我们不等了。
所以它必须和 `-1/-4` 分开统计 —— 前者多半是环境慢，后者是链路或配置错。

> ⚠ 想知道任何 `moveit_msgs` 消息的字段，`ros2 interface show moveit_msgs/action/MoveGroup`
> 会**无限递归**（`RobotState` 自引用）把终端刷爆。正确做法是直接读安装介质：
> `sed -n '1,80p' /opt/ros/jazzy/share/moveit_msgs/msg/PlanningRequestAdapterRequest.msg`。

## 3. 三段计时，以及它们必须满足的关系

| 量 | 怎么测 | 含不含 |
|---|---|---|
| `plan_s` | 客户端发出 goal → 拿到 result | 规划 + action 往返 + move_group 内部开销 |
| `plan_srv_s` | 服务端自己在 result 里报的 `planning_time` | 纯规划 |
| `traj_s` | 轨迹最后一点的 `time_from_start` | TOTG 时间参数化后的运动时长 |
| `exec_s` | 发执行 goal → 拿到 result | 运动时长 + 控制器整定 + 往返 |

正常运行必须满足 `plan_srv_s ≤ plan_s` 且 `traj_s ≤ exec_s`。
**不满足就是信息**：`plan_s` 远大于 `plan_srv_s` ⇒ move_group 到 OMPL 之间的
场景/碰撞检测开销；`exec_s` 远大于 `traj_s` ⇒ 控制器在追轨迹起点
（`allowed_start_tolerance: 0.01` 那条看门狗）。实测十四次 full 运行里（含两次缺陷现场）：
`plan_s` 合计 0.1155~0.2972 s，`exec_s` 合计 16.0379~16.1296 s，`Σtraj_s ≈ 15.6` ——
每条都留有 0.03~0.08 s 的余量给执行侧，全部在 1.2× 缩放因子内。

## 4. 就绪等待：READY 行的四项

`wait_ready()` 不做任何 `sleep` 猜时间，四项分别轮询、分别报错：

| # | 检查 | 超时 | 失败动作 | 典型成因 |
|---|---|---|---|---|
| 1 | `/move_action` action server | 90 s | **ERROR + 退出 3** | move_group 没起 |
| 2 | `/execute_trajectory` | 20 s | **ERROR + 退出 3** | `moveit_controllers.yaml` 没被 `trajectory_execution()` 发现 |
| 3 | `/joint_states` 收到新消息 | 30 s | **ERROR + 退出 3** | `joint_state_broadcaster` 未激活 |
| 4 | JTC 的 `follow_joint_trajectory` **被发现** | 20 s | **只 WARN** | DDS 发现竞态（§8） |

第 4 项故意不做成硬失败，理由要写清：它确实是本项目需要的（否则第 1 条点位偶发 `-4`），
但 `jtc_action` 这个名字是**部署相关**的 —— 换真机或拆成两个控制器时路径就会变。
做成硬失败会让"改了控制器名"表现为"节点起不来"，反而更难查。
真正的兜底是 `execute()` 里的有限重试，两者叠加才够。

探测本身**永远不发目标**：只建一个 `ActionClient(self, FollowJointTrajectory, ns)` 然后
`server_is_ready()`。自己的客户端能看见这个 server，说明它已进 DDS 发现表，
move_group 那边的客户端也就绪了。

```
READY move_group=ok execute_action=ok jtc=ok joint_states=118 joints=8 ctrl_state_topic=/arm6_controller/controller_state
```

## 5. 日志字段字典

一次运行 = 三个产物，全部落在 `~/ros2_ws/logs/`，`run_id` 同一个时间戳：

| 产物 | 内容 | 用途 |
|---|---|---|
| `motion_<run>.jsonl` | 第 1 行 config、中间 9 行每条点位（**含完整轨迹**）、末行 summary | 画图、复算、取证 |
| `motion_<run>.csv` | 每条点位一行、18 个标量列（`CSV_FIELDS`；早期归档 17 列，见下） | 表格排序、人看 |
| `motion_run_<run>.log` | launch 全量 stdout | 出问题时看上下文 |

### 5.1 CSV 列（`motion_log.CSV_FIELDS`，顺序即列序）

| 列 | 单位 | 定义 / 来源 |
|---|---|---|
| `idx` `name` `group` | — | 点位序号、名字、SRDF 规划组 |
| `planner` | — | 实际下发的 `planner_id` |
| `plan_ok` | 0/1 | `error_code == SUCCESS`（规划段） |
| `plan_s` `plan_srv_s` | s | §3 |
| `traj_pts` | 个 | `joint_trajectory.points` 长度 |
| `traj_s` | s | 最后一点的 `time_from_start` |
| `path_len_rad` | rad | 关节空间折线长度 `Σ‖q_k−q_{k−1}‖₂` |
| `exec_ok` | 0/1 | 执行段 `error_code == SUCCESS`。**⚠ plan-only 模式下恒为 1**（§5.3），不能当"执行过"的证据 |
| **`exec_attempts`** | 次 | 执行实际尝试次数；`1` = 一次过，`>1` = 首发被"瞬间拒绝"后重试救回。**只看不判**（§7） |
| `exec_s` | s | 执行 action 往返 |
| `track_err_rad` | rad | 执行期间 JTC 自报误差峰值 |
| `track_err_joint` | — | 该峰值属于哪个关节 |
| `arr_err_rad` | rad | settle 之后的稳态 `\|actual − target\|` 最大值 |
| `arr_err_joint` | — | 最不准的关节 |
| `err_code` | — | 最后一次的 MoveIt 错误码，失败时用来分类 |

JSONL 里另有 CSV 放不下的：`target`（目标关节角）、`trajectory{joint_names,times,positions}`、
`arr_err_per_joint`、`arr_err_signed_per_joint`、`achieved_per_joint`、`track_at_s`、
`track_samples`、`ts`、失败时的 `err` 字符串。

### 5.2 四条实现约定，都是踩过坑换来的

- **机器行用裸 `print`，诊断用 `get_logger()`**。`ros2 launch` 会给 logger 输出加
  `[waypoint_mover-5] ` 前缀和时间戳，`grep -o 'MOTION .*'` 就得先剥一层。
  裸 stdout 保证结果行可直接被 shell 判定（`run_waypoint_demo.sh:94` 就是这么判的）。
- **每条点位先落盘 + `flush()`，再进判据列表**。某一条把节点炸了（回调异常、
  消息字段变更），前面的记录仍然完整可读。阶段一吃过"崩了就没证据"的亏，这里不再赌。
- **总结只进 JSONL，不进 CSV**。CSV 是"一条点位一行"的表，末尾多一行会毁掉 Excel 的排序/筛选。
- **列按名字读，不按位置读**。`exec_attempts` 是在第 6 次运行之后才加的，
  所以 `motion_20260916-231909.csv` 有 17 列、`motion_20260917-005801.csv` 有 18 列，
  列序也不同。`compare_motion_runs.py` 用 `csv.DictReader` 按表头取列，
  新老 CSV 才能进同一张比对表 —— **如果当初按 `row[11]` 取，加一列就会让历史 12 份日志全部错位**。
  （代价是：新增列不会自动进判据，必须显式加进 `MUST_MATCH`/`SCALE_COLS`，见 §7。）

### 5.3 结果行的机器格式

```
MOTION idx=6 name=place group=arm plan_ok=1 plan_s=0.0167 plan_srv_s=0.0026 traj_pts=30
       traj_s=2.8944 path_len_rad=3.5155 exec_ok=1 exec_attempts=1 exec_s=2.9331
       track_err_rad=0.000842 arr_err_rad=7.3e-05 err_code=1

MOTION-SUMMARY n=9 plan_ok=9 exec_ok=9 retries=0 max_arr_err_rad=0.00010 tol_ratio=0.03
               max_track_err_rad=0.00084 plan_s=0.2972 exec_s=16.1192 path_len_rad=11.434
               RESULT PASS (ok)
```

PASS 判据（`motion_log.evaluate()`）只有三条：`plan_ok==n` ∧ `exec_ok==n` ∧
`max(arr_err/tol) ≤ 1`，外加一条病态检查 `max(track_err) ≤ 0.10 rad`。
手指组容差放宽到 `5e-3`（它的 `stopped_velocity_tolerance` 也更松）。
**刻意不把路径长度和规划耗时写进判据** —— OMPL 是随机规划器，这两项天然抖动，
放进判据只会制造假故障。它们进日志、进图，不进 PASS。

> ⚠ **`MOTION-SUMMARY` 里没有 `mode=` 字段，plan-only 的那行看着和 full 一模一样**。
> plan-only 不执行轨迹，节点于是把 `exec_ok` 记成 1（`waypoint_mover.py:435`，
> 否则每次只规划的运行都会被判 FAIL），结果是 `exec_ok=9 … RESULT PASS (ok)`
> 空洞为真 —— 这是本项目里最容易被误读的一行判据。
> 光从盘上区分只看两点：`exec_s` 全为 `0.0`，以及 JSONL 的 `trajectory` 字段不存在。
> 现在 `run_waypoint_demo.sh` 会把模式写进 **`logs/demo_<run>.log`**
> （第一行 `run_id=… mode=plan-only bringup_ttl=…`，末尾 `DEMO-RESULT PASS mode=…`），
> 因为以前模式只存在于当时滚走的终端输出里，`logs/motion_run_20260917-005329.log`
> 单独拿出来无法自证是 plan-only —— 判据落不了盘就等于没写。

## 6. 三个误差指标，以及跟踪误差的物理含义

| 指标 | 定义 | 测的是 |
|---|---|---|
| `arr_err_rad` | `\|q_final − q_target\|`，**settle 0.6 s 之后**取 | 精度：MoveIt 目标容差与 JTC 容差是否对齐 |
| `track_err_rad` | 执行过程中 `\|q_ref − q_fdb\|` 的峰值（JTC 自己算的） | 链路：控制器有没有在追 |
| `path_len_rad` | `Σ_k ‖q_k − q_{k−1}‖₂` | 迂回度：随机规划器两次轨迹差多少 |

三个要点：

1. **`arr` 与 `track` 不可互相替代**。mock hardware 会**完美**跟踪参考
   （`state_following_offset: 0.0`，见 03 §7），所以 `track_err` 小只能证明"链路通"；
   真正反映容差配置的是 `arr_err`。
2. **`arr` 必须在 settle 之后取**。JTC 是"轨迹走完就结束"，但轨迹结束瞬间仍在整定，
   立刻取会把"还没追平"当成误差。settle 是 `settle_time` 参数，默认 0.6 s。
3. **不跨关节、不跨点位求平均**。先平均会把"左右各偏 0.002 rad"抵消掉。
   一律逐关节取绝对值再取 max（`max_abs`），带符号值另存一列只给画图用。

### 6.1 ★ 跟踪误差不是轨迹属性，是"参考速度 × 反馈相位滞后"

这是本项目最重要的一条数据分析结论。直觉上 `track_err_rad` 应该由轨迹决定，但实测十二次回归运行里它能在同一条点位上差
**6.8 倍**（`idx=4 pick`：`4.13e-3` vs `6.04e-4`；三次并发次 `013005=8.05e-4`、`083559=9.64e-4`、`112954=8.07e-4` 都落在中间，比值不变）。
用同一批数据把它拆开，因果链是这样的：

| 观察 | 数据 | 排除了什么 |
|---|---|---|
| 参考轨迹逐次几乎一样 | 轨迹点最多差 `1.7e-4 rad` | 不是"每次规划出不同路径" |
| `exec_s` 不漂：12 次合计 16.1141~16.1282 s（相对散布 0.087%）、运动段逐点位比值 ≤1.0115 | 见 §7 表 | 不是速度缩放漂了 |
| `track_samples` 不是散量 | 十二次 full 里**十一次 = 229**，唯一例外 `005801` = 228（少一个反馈采样，≈ 10 ms）；并发次 `013005`、`083559`、`112954` 都是 229 | **不是丢采样**：228 那次的 Δt = 0.63 ms 还在中位数以下，而 229 的 `233006` 却是 3.04 ms —— 两者不相关 |
| 峰值都落在该关节速度最高的那一小段 | `track_at_s` | 是速度相关量 |
| 绝对误差最大者**倾向于** `place`（`joint6` `v_max=1.778 rad/s`，全序列最快一段） | 逐次取该次 `max(track_err_rad)` 的点位：12 次里 8 次是 `place`，另 4 次是 `pick`(×3) 与 `up_final`(×1)；而这 12 次里有 11 次的最大误差关节都是 `joint6` | 同上 —— 但**"恒为"是错的**（旧版这么写；重数表格时发现 `013005`/`083559`/`233006`/`002500` 四次各由别的点位顶上去，正是那几次 Δt 抖到别处的表现） |

于是把误差除回去 —— **Δt = track_err_rad / v_max**，单位是"反馈落后参考多少毫秒"。

**判据边界从哪来**：`controller_manager.update_rate: 100` ⇒ 控制周期 10 ms。

真故障。这个阈值不是拍的，是测出来的：

```
RATE /arm6_controller/controller_state 99.974
RATE /arm6_controller/joint_trajectory IDLE-NO-PUB
```

**这条实测顺带纠正了一个配置误解**：`ros2_controllers.yaml` 里写着
`state_publish_rate: 50.0`，但它**既不节流 `/joint_states` 也不节流
`controller_state`** —— 两个 topic 都跟随 `update_rate: 100`（另一组独立测量：100.017 / 99.991）。
原因：`JointStateBroadcaster` 有自己的发布节拍，而 JTC 的 `state_publish_rate`
只作用于它自己的 OGM 反馈消息。**所以控制周期要读实测值，不能读 yaml。**
同理 `IDLE-NO-PUB` 说明 `/arm6_controller/joint_trajectory` 空闲时完全不发 ——
用 `ros2 topic hz` 等它是不成立的，只能等 `controller_state`。

> 附带记录一个**脚本 bug**（证据保留在 `logs/controller_rates_20260916-234245.txt:11-12`）：
> 第一版写的是 `timeout 12 ros2 topic hz ... | tail || echo "无消息"`。
> `timeout` 到点返回 **124**，于是"明明有消息"的 topic 也被标成无消息 ——
> 同一个文件里 `average rate: 100.007` 下一行就印着"12s 内无消息"。
> 修法是**先落盘、再 `grep 'average rate'`**，绝不用退出码判断有没有消息。

plan-only 那两行的 `Σpath_len` 是 **14.75** 而不是 11.43 —— 不是路径变长了，
而是**根本没执行**：每个点位的规划起点都停在同一个真实位形（home），
于是 `up_final` 从"上一目标 `extended` 之后"变成"从 home 直接转 π/2"
（`MOTION idx=9 … path_len_rad=1.5708`，正好 90°）。
**所以 plan-only 的运行连几何类指标也不可比**，它只证明规划接口通。

脚本把列分成三类，这本身就是一次设计决策：

```python
MUST_MATCH   = ["name", "group", "plan_ok", "exec_ok"]          # 必须逐字相同
SCALE_COLS   = ["arr_err_rad", "exec_s", "traj_s", "plan_s"]    # 看比值，>5 视为量级变化
VELOCITY_SCALED = ["track_err_rad"]                             # 先除以 v_max 再判
```

`v_max` 从同名 JSONL 的 `trajectory{joint_names,positions,times}` 现算，
所以判据不需要额外记录字段 —— 数据里已有的东西不要再抄一份到别处维护。

比值类指标的实测跨次散布（**前两轮** 11 份参与次逐点位重算；第 12 份 `112954` 归档后这段没有重算）：`exec_s` 运动段（idx≥3）**1.0011~1.0115**，
idx=1 那一段是 **1.0872** —— 别被这个数吓到，它的绝对量只有 `0.0814~0.0885 s`（差 7 ms），
比值大纯粹因为分母小；`arr_err_rad` 逐点位比值最大 **1.66**（idx=7：`5.9e-5` vs `9.8e-5`），
但 11 次全部运动点位的值都挤在 `5.9e-5~9.9e-5` 这一个数量级带里、只用到容差的约 **3 %**（`tol_ratio=0.03`）
⇒ 这里的比值是**小分母噪声**，不是退化（比值关卡阈值定在 5 而不是 1.5，就是为了不被它绊倒）；
`traj_pts` 恒等，`path_len_rad` 全序列合计 11.4338~11.4345（相对散布 **6e-5**），
`Σexec_s` 16.1141~16.1282 s（相对散布 0.087%）。

> `path_len` 这么稳定**不代表 RRTConnect 是确定性的**：这套点位没有障碍、起点固定、
> 每段都是同组关节的小角度移动，随机树落在同一条"顺路"解上。
> 换到有障碍/需要绕行的场景，这个量会真实抖动 —— 所以它留在日志和图里，绝不进 PASS 判据。

排除有三层，**一层是人给的，两层是脚本自己判的**：

```bash
# 唯一的规范命令：16 份 CSV → 12 份进比对
python3 scripts/compare_motion_runs.py --col track_err_rad --exclude 234501,231533 \
        motion_2026*.csv motion_rviz_2026*.csv

#   → logs/compare_20260917-112953_concurrency.txt（上一版 11 份：-083601_concurrency.txt；10 份：-final10.txt）
```

`--exclude` 只留**真正需要人判断**的那一类：`231533`/`234501` 各自记了一个真实 bug
（空 CSV、DDS 发现竞态），删掉就没取证，混进比对又会让每次回归都 FAIL。
**按名字排除**是"留证据"与"不污染回归集"之间唯一干净的做法。

另两类由脚本自己认（`compare_motion_runs.py:195-205` 与 `:227-231`），都印 `EXCLUDED` 行：

1. **plan-only 自动出局**：每一行都 `exec_s=0` 且 `plan_ok=1` ⇒ 只规划不执行，
   不参与任何列（印 `EXCLUDED … 原因 plan-only（9 行全为 exec_s=0…）`）。
   这条以前抄在每个调用方的 `--exclude` 名单里（`,005329,011057`），
   而名单会随运行数增长、抄在 shell 与文档里迟早和实际数据不一致 ——
   **判据的名单也要有单一真源**。
   （顺带撤回本文档早先一句错的说明："plan-only 仍会上 MUST_MATCH 那张表"；
   实际是它的 `exec_s=0` 会让比值列直接 FAIL，所以才被迫在每处手工排除。）
2. **算不出 `v_max` 的运行不参与速度列判据**，其余运行照常按 Δt 判。
   这条是被一个假 FAIL 逼出来的 —— 旧写法是 `have_vel = all(...)`，
   任何一份缺 trajectory 的 CSV 会让**整批**退回"直接比原始值"，
   于是 §6.1 已经定性的 3.04 ms 相位抖动被重新报成：


完整现场留档在 `logs/compare_before-fix_false-FAIL_005801.txt`。
**判据降级比判据缺失更危险**：它照样输出一个看起来很有道理的 PASS/FAIL，
而读者已经无法从结果行看出判据换过一套。所以结果行的后两个字段
`N excluded, M plan-only` 恒定出现 —— 一张比对表少了谁、少了几份，看结论行就知道。
Δt 表同样自己印列身份（`DT cols=…` 与每列一行的 `DT max …`，`:270`、`:312`），

## 8. 一次真实故障的完整闭环

**现象**（`run 234501`）：`MOTION-SUMMARY ... exec_ok=8/9 ... RESULT FAIL`，
第 1 条点位 `exec_ok=0 err_code=-4`，且 `exec_s=0.0029`。

```
MOTION idx=1 name=up ... plan_ok=1 traj_pts=1 exec_ok=0 exec_s=0.0029 err_code=-4
```

**关键线索是 `exec_s` 只有 3 ms** —— 一条 85 ms 才能跑完的最小执行，3 ms 就"失败"了，
说明根本没进控制器。回到 `logs/bringup_20260916-234501.log:152-153`：

```
[move_group-2] [ERROR] [follow_joint_trajectory_controller_handle]:
    Action client not connected to action server: arm6_controller/follow_joint_trajectory
[move_group-2] [ERROR] [trajectory_execution_manager]:
    Failed to send trajectory part 1 of 1 to controller arm6_controller
```

**根因**：JTC 已经 `active`，但 move_group 这个 DDS 参与者**还没发现**它的 action server。
这是竞态，不是配置错 —— 而且它会自愈（第 2 条点位就正常了）。

### 8.1 `-4` 有两种，必须能分开

| | (a) DDS 发现竞态 | (b) JTC 真拒绝轨迹 |
|---|---|---|
| `exec_s` | 几毫秒 | 几毫秒 |
| 重试 | **下次就好** | **永远失败** |
| bringup 日志 | `Action client not connected` | JTC 自己的 rejection 原因 |
| 典型配置成因 | 起栈与跑节点贴得太近 | `allow_partial_joints_goal: false` 时按 group 下发部分关节目标 |

两者同样"秒回"，所以**判据只能是"有限重试 + 每次都留痕"**，
不能无限重试 —— 无限重试会把 (b) 永久藏起来。

```python
INSTANT_REJECT_S = 0.20
instant = info.get("err") == "goal_rejected" or (
    int(info.get("code", 0)) == CONTROL_FAILED and float(info.get("exec_s", 1.0)) < INSTANT_REJECT_S)
if not instant or attempt > self.p_retries:
    return False, info          # 真跑起来后才失败的：绝不重试
```

**两层修复**：`wait_ready()` 第 4 项做发现探测（消除竞态窗口）+ `execute()` 有限重试兜底
（`exec_retries` 默认 3，设 `0` 回到严格模式用于确认竞态是否仍在）。
日志侧新增 `exec_attempts` / `retries` 两个**观测项**：评审要能看出"9/9 一次过"还是"首条重试了 2 次"。

**验证**：用触发它的那套时序原样重跑（探测脚本刚结束、立刻起 demo），
两次结果都是 `exec_ok=9/9 retries=0 RESULT PASS`（`235143`、`235305`）。

### 8.2 顺带：怎么区分"故障"和"每次都有的噪声"

同三次的 bringup 日志计数：

| 日志行 | PASS(235143) | PASS(235305) | FAIL(234501) | 结论 |
|---|---|---|---|---|
| `Found empty JointState message` | 27 | 27 | 27 | **噪声**，与结果无关 |
| `No 3D sensor plugin(s) defined` | 1 | 1 | 1 | **噪声**，`sensors_3d.yaml` 按设计为空（04 §1） |
| `Action client not connected` | 0 | 0 | **1** | **判别量**，只看这个 |

ERROR 级别的行不一定是故障 —— **判据是它在 PASS 和 FAIL 里计数是否不同**，
不是它的日志级别。这一条会决定 07 里每一行的"怎么确认修好了"。

## 9. 已知边界情况（都写在代码注释里，文档只是索引）

- **`idx=1 up` 的零位移**：起点即终点，TOTG 只给 1 个轨迹点
  （`traj_pts=1 traj_s=0.0 exec_s≈0.083 arr_err=0`）。它验证的是链路，不是运动。
  比对脚本对它不做比值判断（0/0）。
- **plan-only 模式**：`execute:=false` 时 `exec_ok` 记 1、`exec_s` 记 0。
  否则"只规划"的快回归会被判成 FAIL。这是刻意的语义约定，不是偷懒。
- **`_start_state` 用的是理论终点**（上一条规划结果的最后一点），不是反馈值。
  mock hardware 下两者相同；真机上应改成重读 `/joint_states`。
  影响面可量化：它只参与 `path_len_rad` 的段首点，误差上界就是 `arr_err ≈ 1e-4 rad`，
  相对段长度 0.04~3.5 rad 可忽略。
- **夹爪是 prismatic，单位是 m 不是 rad**：`grip_open` 的 0.040 是行程
  （= URDF 的 `f_stroke`）。`check_limits.sh` 第 3 条规则专门拦这个单位错配。
