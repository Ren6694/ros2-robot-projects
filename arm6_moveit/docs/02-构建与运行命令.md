# 02 构建与运行命令

> 所有命令都在 WSL 里执行；从 Windows 侧调用统一走 `ssh ros2vm "cd ~/ros2_ws && bash scripts/xxx.sh"`。
> 每个脚本都自带"结果行"（`*-RESULT`），退出码即验收结论，不需要人读日志。

## 1. 构建

```bash
bash scripts/build_ws.sh                          # 全量
bash scripts/build_ws.sh --packages-select arm_demo   # 只重建一个包
```

脚本内部实际执行的命令：

```bash
colcon build --event-handlers console_direct- console_cohesion+ --base-paths src "$@"
```

三个参数都不是装饰：

| 参数 | 原因 |
|---|---|
| `console_direct- console_cohesion+` | 默认输出会把 3 个包的日志交织在一起，报错时看不出是哪个包炸的；cohesion 模式按包整块输出 |
| `--base-paths src` | 不写的话 colcon 会连 `logs/`、`artifacts/` 一起扫描（阶段一踩过），既慢又可能误认 CMake 包 |
| 输出重定向到 `logs/colcon_build_<stamp>.log` 并显式回显 `rc` | `colcon build` 失败返回非 0，但脚本里只要 `tail` 一下就把失败吞了。本项目要求"报错要么自动修，要么给完整排查"，所以 rc 必须落到日志和退出码上 |

实测构建耗时（同一台机器、3 个包）：

```
colcon_build_20260916-231522.log   Summary: 3 packages finished [2.52s]
colcon_build_20260916-231907.log   Summary: 3 packages finished [1.93s]
colcon_build_20260916-233003.log   Summary: 3 packages finished [2.32s]
colcon_build_20260916-235140.log   Summary: 3 packages finished [2.47s]
colcon_build_20260917-001841.log   Summary: 3 packages finished [1.54s]
colcon_build_20260917-004011.log   Summary: 3 packages finished [1.91s]   # 收尾回归
```

结尾固定一行结果行（与其余脚本同形，见 §3）。下面这行是收尾回归
（`colcon_build_20260917-004011.log`）的真机输出，不是模板：

```
BUILD-RESULT PASS Summary: 3 packages finished [1.91s] elapsed=2s log=logs/colcon_build_20260917-004011.log
```

`elapsed`（脚本口径，含 `source ros_env.sh`）比 colcon 自己报的 `Summary` 略大是正常的，
两者量的不是同一段时间；比较构建快慢要用 `Summary` 那一列。

## 2. 运行：三种粒度

```bash
# (a) 只起模型看 TF/外观，不需要 MoveIt
ros2 launch arm_description display.launch.py

# (b) 起完整仿真（rsp + move_group + ros2_control(mock) + 两个控制器 + rviz）
ros2 launch arm_moveit_config moveit.launch.py                 # 带 rviz，手动交互
ros2 launch arm_moveit_config moveit.launch.py use_rviz:=false # 无头，回归用

# (c) 只跑点位节点（要求 (b) 已经在跑）
ros2 launch arm_demo waypoint_mover.launch.py execute:=false        # 只规划，最快
ros2 launch arm_demo waypoint_mover.launch.py execute:=true \
    log_dir:=~/ros2_ws/logs run_id:=20260916-235143                 # 规划+执行+落盘
```

一键版（脚本自己管 bringup 的生命周期，跑完自动收摊）：

```bash
bash scripts/run_waypoint_demo.sh                # = full，bringup 寿命 240 s
bash scripts/run_waypoint_demo.sh plan-only      # 只规划：约 25 s，适合提交前快速回归
bash scripts/run_waypoint_demo.sh full 240       # 显式给 bringup 更长寿命
```

它做的事：后台 `timeout $TTL ros2 launch arm_moveit_config moveit.launch.py use_rviz:=false`
→ 等 action 就绪 → 前台跑 `waypoint_mover` → `grep` 出所有 `MOTION*` 行 →
没有 `PASS` 就 `tail -40` 并把 bringup 日志里的 ERROR/WARN 一起打出来 →
最后一行 `>>> DEMO-RESULT PASS mode=full jsonl=... csv=...`。

> **为什么不做成"一个 launch 拉起全套"**：把 bringup 和点位节点塞进同一个 launch，
> 失败时无法区分是仿真没起来还是节点逻辑错了，而且 `ros2 launch` 会给每行日志加
> `[process-5]` 前缀，机器解析要先剥一层。现在的切法是：bringup 归 bringup（日志
> `logs/bringup_*.log`），节点归节点（日志 `logs/motion_run_*.log`），中间靠
> `wait_ready()` 显式握手。理由写在 `src/arm_demo/launch/waypoint_mover.launch.py` 头部。

## 3. 取证与验收脚本

| 脚本 | 结果行 | 产物 | 什么时候跑 |
|---|---|---|---|
| `build_ws.sh` | `BUILD-RESULT PASS/FAIL` | `logs/colcon_build_<stamp>.log` | 任何源码/配置改动之后（见 §1） |
| `check_limits.sh` | `CHECK-RESULT PASS/FAIL (N issues)` | stdout | 不启 ROS，纯静态核对：限位、速度取小值、点位是否可达（原理与反例见 03 §7） |
| `check_visual_envelope.py`（Windows 侧 `python`，纯离线） | `ENVELOPE-RESULT PASS/FAIL (max 侧向 … mm, 端面 … mm, N 个 link 超限)`；带 `--collision-baseline` 时再印一行 `BASELINE-RESULT PASS/FAIL`；`--selftest` 印 `SELFTEST-RESULT PASS/FAIL` | stdout（留档重定向到 `logs/envelope_<日期>.txt`） | **改过任何 `<visual>` 之后**。判两件事：collision 是否被顺手改了、visual 有没有凸出到"看着穿模而规划不认"（阈值与三条规则见 03 §8） |
| `gen_viewer_parts.py`（Windows 侧 `python`） | `VIEWER-RESULT PASS (N 个零件 / M 种材料 …)` / `FAIL 原因` | 写 `arm6-viewer.html` 的标记区；`--check` 不写盘 | 改了 URDF 的 visual 或材料之后，让浏览器预览页跟上（为什么改成生成而不是手抄，见 06 §11） |
| `probe_moveit_interfaces.sh` | `PROBE-RESULT PASS actions=N services=N topics=N` | `logs/moveit_interfaces_<stamp>.txt` | 怀疑运行图和预期不一致时（action/topic/service/node 全量清单 + `ros2 control list_controllers` + `/joint_states` 抽查） |
| `probe_controller_rates.sh` | `RATES-PROBE DONE` + 每 topic 一行 `RATE <topic> <hz>` | `logs/controller_rates_<stamp>.txt` | 改了 `update_rate`/`state_publish_rate` 之后，验证参数**真的生效**（实测结论见 05 §6.1） |
| `update_collisions.sh [trials]` | `COLLISION-RESULT CONVERGED pairs=N` / `DIFF old=N new=M` | `artifacts/arm6_calculated.srdf` | 改了任何 link 几何之后重算碰撞矩阵（方法学与收敛表见 04） |
| `run_waypoint_demo.sh [full\|plan-only] [ttl]` | `DEMO-RESULT PASS/FAIL` | `logs/motion_<stamp>.{jsonl,csv}`、`logs/demo_<stamp>.log`（结果行**与所用 mode 一起落盘**，否则事后无法判断那个 PASS 是规划还是执行） | 每次改动后的主回归 |
| `capture_rviz.sh [xvfb\|wslg] [RES]` | `CAPTURE-RESULT PASS/FAIL`（由 `SHOT … PASS` 与 `FRAMES-RESULT PASS/FAIL` 两级判据决定） | `artifacts/rviz_<stamp>_{idle,moving,final}.png` | 需要"能看见在动"的截图时（WSLg 陷阱与截图判据见 06；**Xvfb 只在 WSL Ubuntu-24.04 里有**，VM 里没装） |
| `check_rviz_frames.py <idle> <moving> <final>` | `FRAMES-RESULT PASS/FAIL mv_norm=… fn_norm=… arm_bbox=…`（另印 `ARM bbox … 视口占比=…`） | stdout | **对归档图离线重跑内容判据**（"只换尺子不重截"）。判据分母是手臂自己的投影面积，改取景不用重跑仿真；推导与三批验证见 06 §7.1 |
| `plot_motion.py --log <jsonl> [--final]` | `PLOT-RESULT PASS/FAIL` | `artifacts/motion_*_{profiles,metrics}.png` + `_series.csv` | 每次回归后出图；`--final` 产出交付版 |
| `compare_motion_runs.py --col <列> [--exclude ...]` | `COMPARE-RESULT PASS/FAIL (i issues, w warns, N excluded, M plan-only)`，Δt 表自带 `DT cols=…` 与每列 `DT max <run> <ms> ms` | stdout（留档重定向到 `logs/compare_<用途>.txt`） | 跨次一致性判定（回归到底稳不稳）；plan-only 次由脚本自己认出并剔除 |
| `check_concurrency.sh [N] [基线stamp]` | `CONCURRENCY-RESULT PASS/FAIL`（**第一判据是时间窗重叠率**，`overlap_frac ≥ 0.7`；不足 ⇒ 判"测试无效"，后面的 Δt/ADC 数字被标成**仅供参考**不得进结论。其次 `dt_max_ms < 10`、`embed_ok=N/N`（N 次采集都跑完）、**`embed_phys=N/N`（关卡：每一次采集都逐次与基线比过，边沿/检出/`max\|err\|` 精确同 + `MAE ≤ 0.02 mm` + `n ± 1`；少跑一次直接 FAIL）**、`embed_same`（逐格是否相同，**只印不判**，见 05 §6.1 两态对齐）、`demo=PASS`） | `logs/concurrency_<stamp>.txt` + `logs/compare_<stamp>_embed_<i>.txt` + 一次 ROS full 回归 + N 次阶段一采集 | 改任一栈的调度/周期后，验证两栈同机并发互不干扰（结论边界见 05 §6.1）。关卡自身的正/负对照留在 `logs/concurrency_gate_selftest_20260917-081450.txt`：三条窗口 `frac=0.96 rc=0`，只喂一条 `frac=0.04 rc=1` |
| `selftest_embed_gate.sh` | `EMBED-GATE-SELFTEST PASS/FAIL positive=N/M negative=K/K` | `logs/embed_gate_selftest_<stamp>.txt` | **改动关卡表达式之后、引用 `CONCURRENCY-RESULT` 之前**。正对照喂 6 份真实归档采集（必须全 OK），负对照把基线那串字段逐项改坏（边沿 −1 / `max\|err\|` +0.1 / MAE +1 mm / `n` +5 / 删掉 `n`），**每一项都必须被点名列出** —— 没见过 FAIL 的判据不能信 |
| `embed_gate.py`（被上面两个脚本调用） | `OK` / `summary-missing` / `"<字段 a->b> …"` | stdout | 并发关卡的**表达式真源**：`n ±TOL_N`、边沿/检出/三面 `max\|err\|` 精确、三面 MAE `±TOL_MAE`。抽成文件就是为了让它能被单独证伪 |
| `phys_from_summary.sh`（被 source，不单独跑） | — | — | 从阶段一 `plot_summary_*.md` 抽那 9 个验收量的**唯一一份**抽取规则；关卡和自测共用，否则自测通过只证明一份拷贝是对的 |
| `sync.sh` / `fetch_artifacts.sh` | — | — | Windows→WSL 推源码；WSL→Windows 拉产物，方向严格单向 |

`plot_motion.py` 的 `PLOT-RESULT` 不是"文件生成了没"，而是**图里的数据自洽**：
条数与 JSONL 一致、全局时间轴单调、每条轨迹 `time_from_start` 单调、
关节维度一致、`plan_ok` 全 1、到位误差在容差内。任一条不满足就 `FAIL` 并列 `PLOT-ISSUE`。

## 5. 调试常用命令（本项目实际用到的）

```bash
source scripts/ros_env.sh            # 任何手工调试前先跑这个

ros2 node list / ros2 topic list -t  # 运行图对不对
ros2 daemon stop && ros2 daemon start   # "明明在发但 list 看不见" 九成是 daemon 缓存
ros2 topic echo /joint_states --once
ros2 topic hz  /arm6_controller/controller_state --window 100
ros2 interface show moveit_msgs/action/MoveGroup   # ⚠ 见下方警告
ros2 param get /move_group robot_description_semantic
ros2 control list_controllers        # 注意是下划线，不是 list-controllers
ros2 control list_hardware_interfaces
ros2 launch arm_moveit_config move_group.launch.py debug:=true   # gdb 起 move_group
```

两条实测教训：

1. **`ros2 interface show moveit_msgs/action/MoveGroup` 不能用**。它的 `Result` 里含
   `RobotState`，而 `RobotState` 自引用（`RobotState attached_collision_bodies`），
   打印会无限递归刷屏。要看字段就去读安装介质：
   `/opt/ros/jazzy/share/moveit_msgs/msg/*.msg`。
2. **`debug:=true` 需要 `launch/gdb_settings.gdb` 存在**。`generate_move_group_launch()`
   无条件把它作为 `gdb -x <文件>` 传入；文件不存在时 `debug:=false` 照样能跑，
   但 `debug:=true` 会在 gdb 启动阶段就失败。这个"看起来没用"的文件必须装进包里，
   里面每条命令（`set pagination off`、`handle SIGPIPE nostop`、`thread apply all bt`）
   的理由都写在文件头部注释。
