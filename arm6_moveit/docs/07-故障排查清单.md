# 07 故障排查清单

> 本篇只覆盖阶段二（ROS 2 Jazzy + MoveIt 2）。阶段三会出一份**合并两阶段**的总手册。
> 每一行都对应本项目**真实发生过**的一次故障，`证据` 列给的是仓库里可直接打开的文件与行号。
> 没发生过的"理论可能"不写进来 —— 那种清单对排查没有帮助。

## 0. 用法

先跑 §1 的自检，五个结果行会告诉你问题在哪一层；只有出现 FAIL 才需要往下查表。
查表时**按症状找**，不要按"我改了哪个文件"找 —— 本项目一半的故障，症状和成因不在同一层。

## 1. 一分钟自检（远端 `~/ros2_ws`）

```bash
bash scripts/build_ws.sh                                  # BUILD-RESULT PASS
bash scripts/check_limits.sh                              # CHECK-RESULT PASS
bash scripts/probe_moveit_interfaces.sh                   # PROBE-RESULT PASS
bash scripts/run_waypoint_demo.sh plan-only                # DEMO-RESULT PASS (mode=plan-only)
bash scripts/run_waypoint_demo.sh full                     # DEMO-RESULT PASS (mode=full)
```

各步失败指向的层：

| 失败在哪 | 说明问题在 |
|---|---|
| `build_ws.sh` | 包结构 / `setup.py` 的 data_files / 依赖没装 |
| `check_limits.sh` | URDF `<limit>` ↔ `joint_limits.yaml` ↔ SRDF ↔ waypoints 四处定义不一致（**不需要起 ROS** 就能抓到） |
| `probe_moveit_interfaces.sh` | 栈没起来，或 action/service 名字与预期不同 |
| `plan-only` | 规划层：模型、SRDF、关节限位、碰撞矩阵、OMPL |
| `full` 而 `plan-only` 通过 | 执行层：ros2_control、JTC 配置、`moveit_controllers.yaml`、DDS 发现 |

截图链路单独一条：`bash scripts/capture_rviz.sh` → `CAPTURE-RESULT PASS`（见 06）。

双工作空间并发也**不在**这一分钟里（第一步要先编一次阶段一固件，之后是 ~30 s 的真实重叠窗口
—— 三次实测的三条采集都首尾相差 26~29 s（`013004` / `083601` 各 28.6 s、`112953` 26.1 s，
由各条 `EMBED` 行的 `start/end` 相减），整条命令 33 s 上下；它会真的去抢 CPU，不该每次自检都跑）：
`bash scripts/check_concurrency.sh 3 <阶段一基线stamp>` → `CONCURRENCY-RESULT PASS`（见 05 §6.1、§3 第 6 条）。

但**关卡本身**的自检可以随手跑，它不起任何栈、只要 1 s：
`bash scripts/selftest_embed_gate.sh` → `EMBED-GATE-SELFTEST PASS positive=6/6 negative=5/5`。
改过 `scripts/embed_gate.py` 或 `scripts/phys_from_summary.sh` 之后必须先跑它，
否则你手里那个 `embed_phys=3/3` 可能是一份恒真的判据印出来的。

### 2.6 脚本自身的坑（这类最难查，因为它骗的是"判据"）

| 症状 | 根因 | 修法 | 证据 |
|---|---|---|---|
| `ros2 topic hz` 明明打印了 `average rate: 100.007`，脚本却报"12s 内无消息" | `timeout` 到点返回 **124**，`cmd \|\| echo 无消息` 于是必然触发 | 先落盘，再 `grep 'average rate'` 判定；**绝不用退出码判断"有没有消息"** | `logs/controller_rates_20260916-234245.txt:11-12`，05 §6.1 |

## 3. ★ 元方法：本项目反复用到的八条

1. **先证伪判据，再怀疑系统。** 四次"故障"最后都是**判据本身错了**：
   跟踪误差差 6.8 倍（量纲：该归一化成 Δt）、截图"全黑"（matplotlib 的 `[0,1]` 浮点）、
   `COMPARE-RESULT PASS` 却非 0 退出（GBK 打印）、`COMPARE-RESULT FAIL` 说"量级变化"
   而同一批数据判 PASS（**判据被静默降级**）。当故障"太严重以致不合理"时，
   先写一个已知答案的输入去测判据（本项目所有校验脚本都做过 negative self-test）。
   第三个例子提醒一种反向症状：**失败发生在结论打印之后**，
   于是终端上同时出现 PASS 和非 0 退出码 —— 这种矛盾几乎一定是判据/输出层的问题，
   不是被测系统的问题。
   第四个例子是前三个的**升级版**：判据不仅会错，还会**在半路换一套**却印同样的结果行。
   所以推出的规则是：**结果行必须自带它用了哪套判据的说明** ——
   `COMPARE-RESULT` 的第三个字段 `N excluded`、Δt 段表头里的"参与 N 份"、结果行第四个字段的
   `p plan-only` 就是这个用途（现行轮次实测：**参与 12 份、plan-only 2 份**，见
   `logs/compare_20260917-112953_concurrency.txt`；上一轮 `-083601` 是 11 份），降级不可能再隐形。
   推论：**判据用到的名单也要有单一真源**。原先每处调用各抄一份 `--exclude 234501,231533`，
   新增一次运行就得记两处；现在 plan-only 由脚本自己从盘上认出（整份 `exec_s=0`），
   判据行第四个字段就是它的票数，人只保留"哪些是缺陷留证"这一份名单。
2. **用计数区分噪声与故障。** 同一条 ERROR 在 PASS 和 FAIL 运行里计数相同 ⇒ 噪声；
   不同 ⇒ 判别量。日志级别不参与这个判断（§4）。
3. **配置值不等于运行值。** `state_publish_rate: 50` 实测不节流任何 topic（100.005 / 99.974 Hz）；
   控制周期、发布率、限位都要**测**，不能读 yaml。见 05 §6.1。
4. **区分"竞态"和"配置错"的判据是能否自愈。** 两者症状完全相同（秒回 + 同一个错误码），
   只有重试行为能分开。所以重试必须**有限且留痕**（`exec_attempts`），否则就把真故障永久藏起来。
5. **缺陷证据不删。** 出过问题的运行（`234501`、`231533`）和被修复前的截图（`233006`）
   都留在仓库里，用 `--exclude` / 文件名把它们挡在回归集之外。
   删掉它们，文档里所有"实测"就都退化成声明。
6. **负载类结论的支撑是"时间窗重叠"，不是"我同时启动了"。** 本轮唯一一次**自己撤回**的结论
   （`005801`，见 §2.6 末行与 05 §6.1 ⚠ 段）属于第 1 条的邻近类，但根因不同：判据没算错，
   是**测试本身没测到它声称测的东西**。所以写成规则：任何"并发下仍然正常"的说法，
   必须先把两边的窗口换算成 `overlap / 被保护时长 ≥ 阈值`，不足就判 `FAIL(测试无效)` ——
   **让无效测试给出 FAIL，而不是让它给出一个碰巧正确的 PASS**。
   代价也要认：撤回不等于删除，原数据（`005801` 仍是有效普通回归次）与撤回说明都留在文档里，
   这样下次读的人才知道这条结论是怎么来的。
7. **打印出来的量必须被判据消费；判据还得能单独证伪。**（§2.6 末行；维护约定见 00 §7 第 8 条）
   `embed_ok=3/3` 骗人的根因不是算错，是**那一格没有任何判据读它**。所以：
   ①每印一个 `X=…` 就要求有一个判据读它，只印不判的字段自己写明 `(not-gated)`
   （本项目现在这样标着 `embed_same=2/3(not-gated)`）；
   ②判据表达式不能内嵌在 shell heredoc 里 —— 那意味着"证伪它"要付一次 33 s 端到端的代价，
   于是没人会去证伪。抽成 `scripts/embed_gate.py` 后正/负对照各一次只要 1 s，
   这才让 `EMBED-GATE-SELFTEST PASS positive=6/6 negative=5/5` 成为可能。
   ★ **当时的验证边界，当日已闭环**：抽函数之后**没有**再跑第三次端到端并发（当时的理由：不想
   再往 15 份 CSV 归档里加一次运行、也不想把"两次并发"的措辞改口；判断依据是改动只有两行调用
   （`python3 scripts/embed_gate.py "$BASE_PHYS" "$CUR_PHYS" …` 与被 source 的抽取函数），
   而自测发出的正是**同一条命令、同一 cwd、同一引号**）。当天上午补了第三次
   （`112953`，11:29）：`CONCURRENCY-RESULT PASS overlap_frac=0.95 dt_max_ms=0.72
   embed_ok=3/3 embed_phys=3/3 embed_same=3/3(not-gated)`，三行 `EMBED-CMP` 全部由脚本自己产出，
   没有任何手工补比 ⇒ 表达式正确性（自测）与"重构后的整条 shell 又跑通了一次"（端到端）现在**各有**证据。
8. **归因要么有判据，要么降级成"机制未测"。**（00 §7 第 9 条）本轮撤掉两条因果句
   （"bringup 高峰扰动 ADC"、"CPU 抢占造成那次 3.04 ms"），两条都是顺手写的、都没有判据。
   可用的归因手段是**与一份无关的归档互比**：`083601` 的三次采集与并发毫无关系的基线
   `005248` 在**被关卡判的量**上全部相同（`edges 8→8`、`detects 4→4`、三面 `max|err|` 精确相等，
   即三行 `phys=OK`），"CPU 被抢 ⇒ ADC 读数漂"这条就立不住；
   至于逐格是否相同，因两面态问题**本来就不参与判定**（见 05 §6.1 与 `embed_gate.py` 头注）。
   反过来，**时间上重合不是证据**
   （`005801` 就是这么假成功的，见第 6 条）。所以写结论时的自检是：这句话里的判据是哪一行输出？
   答不上来就改成"机制未测，只记录了数值"。

## 4. ERROR/WARN 白名单（实测计数，别再去查它们）

**口径**：`logs/` 下 **17 份**"完整栈 bringup"日志 —— 12 份无头 `bringup_*.log` +
5 份 `rviz_bringup_*.log`。其中两份**中途夭折**，例行提示一行都没有：
`rviz_bringup_20260916-232315.log`（启动中途放弃）与
`bringup_20260917-010817.log`（**故意**把 `BRINGUP_TTL` 设成 1 s，用来验证 `DEMO-RESULT FAIL`
那条机器行；只有 14 行日志）。所以"每次"那一列按 **15 份跑完的**读。
最近一次刷新是补测并发（多了 `bringup_20260917-083559.log`）之后做的，
原始输出留在 `logs/census_20260917-090400.txt` —— 下面这张表的每个总数都能在那份里 `grep` 到。
**第三轮并发（11:29）又多了一份无头 `bringup_20260917-112954.log`（跑完，17→18 份、15→16 份跑完），
这张表仍按 09:04 口径，没有随它刷新** —— 要用下面的命令刷新后才会动"总数"那一列。
表里"每次"那一列才是重点 —— **它在 PASS 与 FAIL 运行里相同**，所以是噪声。
新增运行后用同一条命令刷新（它会连"每份多少"一起印出来，别只抄总数）：

```bash
cd logs && OUT="census_$(date +%Y%m%d-%H%M%S).txt" && {
for p in "Found empty JointState message" "planning volume was not specified" \
    "using planner 'RRTConnect'" "No 3D sensor plugin" "Moved backwards in time" \
    "recognize_objects not available" "visual geometry but no collision geometry" \
    "Resolution not specified for Octomap" "Could not enable FIFO RT" \
    "ROS_LOCALHOST_ONLY is deprecated"; do
  tot=$(grep -hc "$p" bringup_2026*.log rviz_bringup_2026*.log | awk '{s+=$1} END{print s}')
  n=$(grep -lc "$p" bringup_2026*.log rviz_bringup_2026*.log | wc -l)
  printf "%-46s total=%-5s files_with_hit=%s\n" "$p" "$tot" "$n"
done
# 必须两个数一起看：`total = 每次 × files_with_hit` 才撑得住"恰好 N 次"这种说法。
# 只印总数会漏掉分布 —— §4 那条"恰好 1 次"的错误就是这么来的
grep -c "Moved backwards in time" bringup_2026*.log rviz_bringup_2026*.log
} | tee "$OUT"
# 想统计"全量"时记得把正在生成的这份排除掉，否则它会数到自己头上（见上面 ⚠）：
grep -rh "ROS_LOCALHOST_ONLY is deprecated" . --exclude="census_*.txt" | wc -l
```
