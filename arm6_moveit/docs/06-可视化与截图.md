# 06 可视化与截图

> 脚本：`scripts/capture_rviz.sh`　配置：`src/arm_moveit_config/config/moveit.rviz`
> 产物：`artifacts/rviz_final_{idle,moving,final}.png`
>
> 这一篇的目标不是"把 rviz 打开"，而是**让"仿真真的跑起来了"变成可复核的图像证据**。
> 为此需要解决三件事：截得到（§1）、截得对（§5、§6）、判得出（§3、§7）。

## 1. ★ 为什么不能用 WSLg 直接截屏 —— 实测出来的结论

本机确实是 WSLg（存在 `/mnt/wslg`，`/tmp/.X11-unix/X0` 由 WSLg 的 Xwayland 提供），
按直觉应该 `DISPLAY=:0` 直接截。实测（已落盘：`logs/wslg_rootwindow_probe_20260917-004912.txt`）：

```
## DISPLAY=:0
  scrot rc=0（表面成功）  12040 B
  shape=(1600, 2560) std=0.00 -> 全黑/无内容
## DISPLAY=:99
  scrot rc=1  报错: scrot: Can't open X display. It *is* running, yeah? [:99]
```

> **root 窗口的宽度不是稳定量**：它是 WSLg 聚合出的虚拟桌面尺寸，
> 取决于当时挂了几个显示（本轮 2560x1600；更早一次量到 5120x1600）。
> 所以要引用的数字只有 `std=0.00` 这一条，尺寸只是"确实截到了一张图"的旁证。
>
> `:99` 报 rc=1 是**正常**的：`Xvfb :99` 由 `capture_rviz.sh` 自己起、自己收，
> 平时并不存在。这也说明为什么脚本不能假设"显示已经在那儿了"。

**根因**：WSLg 把每个 X 客户端窗口单独映射成一个 Wayland surface，
Xwayland 自己的 **root 窗口没有合成内容**。`scrot` 默认截的是 root，
所以必然是黑的 —— 而且它**不报错**，是最容易骗人的一类故障。

**对策**：起一个真正的内存 X 服务器 `Xvfb`，让 rviz2 用 Mesa 的软渲染画进去，
这时截 root 才是真实画面。这也是 ROS 官方 CI 出截图的做法。

```bash
Xvfb :99 -screen 0 1680x1050x24 -nolisten tcp &
export DISPLAY=:99
export LIBGL_ALWAYS_SOFTWARE=1     # WSL 里 GPU 直通不一定可用
export GALLIUM_DRIVER=llvmpipe     # 软渲染慢，但结果确定、可复现
```

脚本保留 `mode=wslg` 分支，将来在真正的 XFCE 会话（`startxfce4` + `:0`）下可以直接复用。
这也解释了 `ros_env.sh` 为什么只在 `gui` 模式下才给 `DISPLAY` 兜底为 `:0` ——
在无头脚本里设 `DISPLAY` 只会掩盖"这个脚本本来不该弹窗口"的事实。

## 3. 怎么知道截到的不是黑图

判据**不能用文件大小** —— 全黑 PNG 压缩后也有几十 KB。用像素标准差：

```python
a = np.asarray(mpimg.imread(path)[:, :, :3], dtype=float)
if a.max() <= 1.0:      # ★ matplotlib 读 PNG 给的是 [0,1] 浮点，不是 0~255
    a *= 255.0
std = float(a.std())    # 判据：std*255 > 3.0 才算有画面
```

那个 `*255` 是踩过才加的：第一版直接拿 `std > 3.0` 判，而 matplotlib 返回的
`[0,1]` 浮点数组正常截图的 std 只有 `0.44` —— 于是**每张正常图都被判成全黑**，
白等 90 s，还以为是 §1 那个 WSLg 问题没解决。
一次故障里同时有两个"看起来都对"的原因时，先把判据本身证伪一遍。

**但 std 只是 liveness 检查，证明不了位形。** 实测三张图的**视口** std：

```
idle 62.92   moving 62.99   final 62.96
```

手臂只占视口百分之十几的像素，全局统计量完全分不出"动了没有"。
所以内容另有一套判据，见 §7。

## 4. 取景：先问窗口几何，再截

Xvfb 的屏幕（1680x1050）比 rviz 窗口（1600x960）大，直接截 root 会带一圈黑边。
先问 `xwininfo` 要顶层窗口 "RViz" 的绝对坐标与尺寸，再用 `scrot -a` 只截它：

```bash
wid=$(xwininfo -root -tree | grep -m1 -E '"RViz"|"rviz2"' | grep -oE '0x[0-9a-f]+' | head -1)
xwininfo -id "$wid" | awk '/Absolute upper-left X/{x=$NF} /Absolute upper-left Y/{y=$NF}
                           /^  Width:/{w=$NF} /^  Height:/{h=$NF}
                           END{printf "%d,%d,%d,%d", x, y, w, h}'
scrot -a 0,0,1600,960 -o artifacts/rviz_..._idle.png      # 实测输出
```

拿不到窗口几何时**自动退回截整屏** —— 宁可丑，也不要因为裁图失败而完全没有证据。

## 5. 相机参数是"看图看出来的"，不是"算出来的"

`moveit.rviz` 里 Orbit 视角原来是这么写的，理由看起来非常充分：

```yaml
Distance: 2.0      # 整臂高 0.94 m，站 2 m 看刚好
Focal Point: {X: 0, Y: 0, Z: 0.35}
```

结果截图里手臂上半截被裁掉了。**算错的地方**：zero 位姿下夹爪顶端实际到 `z≈1.05 m`
（不是 0.94），而 Orbit 默认竖直 FOV 约 0.7 rad，在 2 m 处只覆盖约 0.74 m —— 装不下。
实测改成 `Distance: 3.2` + 焦点抬到 `z=0.52` 才完整入画。

```yaml
Distance: 3.200000047683716
Focal Point: {X: 0.1, Y: 0.0, Z: 0.52}
Pitch: 0.34900001287460327
Yaw: -0.75
```

> 教训写进注释了：**再改小之前先跑一遍 `capture_rviz.sh`，别只看数字。**
> 几何推导能保证"应该看得见"，只有截图能保证"真的看得见"。

**2026-09-30 又改小了一次，而且这次是有理由的**：外观改造（03 §8）之后，
`Distance 3.2` 下整臂只占视口一百来像素，新加的毂/法兰/螺栓圈全部糊成一个点 ——
"完整入画"满足了，"看得清"没满足。实测改成

```yaml
Distance: 1.62
Focal Point: {X: 0.2, Y: 0.0, Z: 0.46}
Pitch: 0.30
Yaw: -1.15
```

在 VM 桌面（1600×1050 窗口）下零位与 `pick` 位形都完整且零件可辨，
两张证据图见 §10。**这条改动随后在 Xvfb 截图管线上复跑过**（09-30 补）：
第一次 `CAPTURE-RESULT FAIL`，根因不是取景、而是 §7 那条判据的分母随取景一起变了
3.9 倍 —— 判据已改成对投影面积归一化，复跑 `CAPTURE-RESULT PASS`
（`stamp=20260930-165553`，同批 `MOTION-SUMMARY … RESULT PASS`）。全过程见 §7.1。
上面那句"再改小之前先跑一遍 `capture_rviz.sh`"因此**当场兑现了一次**：
它确实抓出了东西，只是抓到的不是"裁切"而是"判据本身不尺度无关"。

另外记一句环境口径：`capture_rviz.sh` 这条 Xvfb 路径跑在 **WSL2 Ubuntu-24.04**
（`~/ros2_ws`，有 Xvfb/scrot）；VirtualBox VM「ROS2-Jazzy」里**没装 xvfb**，
那边只能走 §10 那种 `VBoxManage controlvm screenshotpng` 的"看得见窗口"取证。

窗口宽度 1600 也是同一类决定：左侧三个面板固定占掉约 700 px，
窗口再小，3D 视图就成竖条（同时 §7 的视口比对也要按这个比例切）。

## 6. ★ `Loop Animation` 会让截图变成两张互相矛盾的手臂

这是本轮复核自己截图时发现的**真实缺陷**，不是假想。

`artifacts/rviz_20260916-233006_final.png`（旧）里：一只手臂竖直站在原点，
**另一只手臂横躺在地面网格上**。第一反应是"模型/位形错了"。

拆开看是渲染语义问题。MotionPlanning 面板同时画**三套机器人**：

| 机器人 | 数据来源 | 本项目里的值 |
|---|---|---|
| 状态机器人 | `/joint_states` → TF | 真实执行到的位形 |
| 目标机器人 | 最后一次 goal（可拖动的半透明模型） | 目标点位 |
| 规划路径机器人 | `display_planned_path` | 受 `Loop Animation` 控制 |

`Loop Animation: true` 时第三套会**反复重播整条轨迹**，截图在随机相位抓到它。
`up_final` 这条轨迹的**起点**是上一条 `extended`（`joint2=90°`，手臂水平）——
所以"躺在地上的那只"就是重播机器人被抓在轨迹开头，与状态机器人（竖直，`up_final`）同时入画。

修法就是把重播关掉，并把这个理由写进配置注释：

```yaml
Planned Path:
  Loop Animation: false     # 截图必须单义；交互演示时再手动勾上
  State Display Time: 0.05 s
  Trajectory Topic: display_planned_path
```

关掉之后 `final` 只剩一只手臂（新旧两版的量化差异见 §7）。
**旧图不删**，保留在 `artifacts/rviz_20260916-233006_*.png` 作为"改之前"的证据。

同一轮复核还顺手抓到另一处**注释与配置矛盾**：TF 显示的注释写着
"TF 显示是刻意打开的"，下面的值却是 `Enabled: false`。
提交版配置里 TF 确实是关的（十几套坐标轴会把证据截图糊满），
所以改的是**注释**（说明为什么关、什么时候该开），而不是把值改成 true 去迁就一句写错的话。

> 判读提示：`final` 图里底座圆柱表面有橙色竖条纹。那是**多套半透明网格重合**产生的
> 摩尔纹（`Scene Robot: Robot Alpha: 0.5`），不是贴图或模型错误 —— 它只在
> "这条栈曾经规划过轨迹"之后出现，`idle` 那张是干净的。

## 7. 内容判据：三张图必须"不一样，然后又一样"

§3 的 std 管不了位形，所以脚本第 6 步比对**视口区域**的变化像素占比：

```python
def viewport(p):  a = imread(p)[..., :3]*255;  return a[:, int(w*0.44):, :]   # 跳过左侧面板
def changed(x, y): return float((abs(x-y).max(axis=2) > 25).mean()*100)       # 任一通道差>25
```

阈值方向**相反**，两条一起用才不会被"随便截三张不同的图"糊弄过去：

| 判据 | 阈值 | 实测（修 Loop Animation 后，脚本自己印的） | 实测（修之前） |
|---|---|---|---|
| `idle ↔ moving` | **> 0.20%** | 0.58%（`002500`）/ 0.52%（`001901`） | 0.69% |
| `idle ↔ final` | **< 0.35%** | 0.13%（`002500`）/ 0.16%（`001901`） | **0.55%**（地上多了一条重播机器人） |

`idle ↔ final` 只有 0.1~0.2% **不是巧合，而是这条证据的本意**：
`up` 和 `up_final` 是同一个全零目标，两张图几乎相同正是
"机械臂回到了起点"的图像证据（与日志里 `arr_err_rad ≤ 1.0e-4 rad` 对应）。
而修复前那个 0.55% 恰好落在阈值之上 —— 也就是说这条判据**能抓到** §6 那个缺陷，
不是事后编出来的门槛。

任一通道差 >25 的门槛是为了滤掉抗锯齿抖动和右下角 `31 fps` 计数器的数字变化。

### 7.1 2026-09-30：这条判据被"取景"改了，而且是被一次真红改的

外观改造（03 §8）之后把 Orbit 从 `Distance 3.2` 拉近到 `1.62`（不然 73 个零件糊成一团），
同一套流程当场判红：

```
DIFF idle↔moving changed=1.99% OK
DIFF idle↔final  changed=0.69% FAIL(未归位/有多余机器人)     ← 界是 0.35%
CAPTURE-RESULT FAIL mode=xvfb stamp=20260930-164700
```

**先查假因，再谈改尺子**（顺序不能反，否则就是"把判据调到能过"）：

| 假因 | 怎么排除的 |
|---|---|
| 鬼影机器人回来了（§6） | `idle↔final` 的差异像素**只贴着手臂轮廓**：x 跨度 4%→9%、y 跨度 29%→57%，与手臂投影一起放大，不是散布全视口；且 `fn(0.69%) < mv(1.99%)`，鬼影的特征是反过来 |
| 手臂真的没回位 | 同批 `MOTION-SUMMARY n=9 exec_ok=9 max_arr_err_rad=9e-05`，到位误差与旧批同量级 |
| **分母是视口面积，分子随取景长大**（真因） | 量手臂扫过的投影包围盒：旧批 20 016 px、新批 78 364 px，**3.9 倍**；而读数 mv 0.58→1.99、fn 0.13→0.69，涨了 3.4~5.3 倍 —— 同一件事 |

所以改的不是阈值数字，是**分母**：把"变化像素 / 视口像素"换成
"变化像素 / **同一张图里手臂自己的投影面积**"（面积取 `idle↔moving` 差异像素的包围盒，
不需要按颜色分割手臂）。两条判据随之全部变成无量纲比值：

| 判据 | 新阈值 | 09-16 鬼影批 | 09-17 修好后 | 09-30 新取景（两次） |
|---|---|---|---|---|
| [1] `mv_norm` | **> 12%** | 33.5% OK | 24.9% OK | 21.8% / 23.9% OK |
| [2] `fn_norm` | **< 0.6 × mv_norm** | 26.8% vs 界 20.1% ⇒ **FAIL** | 5.6% vs 14.9% OK | 7.5% vs 13.1% / 6.6% vs 14.4% OK |

归一化之后 mv 从 24.9% 落到 21.8%、fn 从 5.6% 升到 7.5% —— 两批落在同一量级，
取景不再进判据。**红样仍然是真的**：鬼影批 [2] 越界 1.33 倍被判 FAIL，
两个绿样余量 1.75~2.7 倍。[2] 一开始写成 `0.8 × mv`，一验发现鬼影批算出来
26.8% vs 界 26.8% —— **正好压在边界上**，这种判据换个批次就翻脸，收到 0.6。

判据同时从 `capture_rviz.sh` 里**抽成独立脚本** `scripts/check_rviz_frames.py`，
因为它现在能对归档图**离线重跑**（"只换尺子不重截"）：上面那张三批对照表就是
拿归档 PNG 跑出来的，一次仿真都没重跑。`capture_rviz.sh` 第 6 步改成调它，
`CAPTURE-RESULT` 从 `FRAMES-RESULT` 取结论；脚本每次还印
`ARM bbox=… 视口占比=…` —— **下次再改取景，先看这个数变了多少**，
而不是等判据红了再去猜。

> 这条的通用形式：**判据里凡出现"占屏幕/占视口/占总数"的分母，就要问一句
> "这个分母会不会跟着我要改的东西一起变"**。这次它跟着变了 3.9 倍，
> 而阈值是拿旧分母标定的 —— 症状就是一次看起来像"改造把机器人改坏了"的假红。

## 8. `moving` 那张到底该等多久

```bash
# 等第 3 条点位的 MOTION 行出现，再 sleep 1.2 s
grep -q "MOTION idx=3 " "$DLOG" && break
```

三个版本迭代出来的：

1. 最初等 `MOTION idx=` 第一条 → `idx=1` 是 `up`（零位移，`traj_pts=1`），
   手臂根本没动，`moving` 和 `idle` 几乎一样，等于白截。
2. 那为什么不等 `MOTION idx=4`？**MOTION 行是在执行结束 + settle 之后才印的**，
   等它出现时手臂已经停在 `pick` 上了 —— 拍到的还是静止位形，不是运动过程。
3. 现在：等 `idx=3` 完成（+1.2 s）⇒ 正处在 `pick`（2.28 s）的约 26% 处，
   手臂在半途，且目标机器人在 `pick` 终点 → 画面里能看到弯折的重影，
   这**恰好**是"规划目标 vs 当前状态"的可视化。

## 11. `arm6-viewer.html`：零件清单改成从 URDF 生成（以及三处一直没跑起来的错）

浏览器里那份零依赖 3D 预览（`arm6-viewer.html`，Canvas 2D 手写的投影/画家算法）
原来把每个 link 的几何体**手抄**成一行 `pushBox` / `pushCyl`。09-30 外观改造把
一个 link 从 1 个几何体变成最多 10 个之后，这条路彻底不可维护 —— 手抄没有强制力，
抄漏了网页照样"画得很像"，只是变成另一台机器人。

现在改成生成：

```bash
python3 scripts/gen_viewer_parts.py              # 读 artifacts/arm6.urdf → 注入标记区
python3 scripts/gen_viewer_parts.py --check      # 只比对不写盘（回归用）
#   VIEWER-RESULT PASS (73 个零件 / 6 种材料，与 URDF 一致)
```

注入区由 `/*__PARTS_BEGIN__*/ … /*__PARTS_END__*/` 两个标记圈定，里面是
`const MAT = {…}`（材料直接从 `<material>` 读）和 `const PARTS = [[帧名, 形状,
x,y,z, roll,pitch,yaw, a,b,c, 材料], …]`。**标记之外**的正运动学、滑块、预设位形
一概不动 —— 关节链没变，变的只是每个 link 画几个几何体。
表外的 link 若带 visual 会直接报错而不是悄悄漏画（`FRAME` 是一张封闭映射）。

### ★ 顺带修掉的三处"这个页面其实一直没渲染过"

改造前它是**空白**的。三处都在，而且没有一处会留下有用的报错：

| 症状 | 根因 | 教训 |
|---|---|---|
| 整段脚本不执行，页面只剩控制面板，控制台只闪一次 | `camBasis()` 里 `sy` 被 `const` 和 `let` 各声明一次 —— 同一作用域重复声明是**语法错**，不是运行时错 | 旁边那个 `sz2` 就是当年为了躲同名改的，改了一个漏了另一个。**躲冲突式改名必须把同作用域的标识符一次扫干净** |
| 一旦跑起来就 `ReferenceError: REACH is not defined` | 参考圈和 HUD 引用的 `REACH` 从来没定义过；HUD 里那个 `0.705` 是手抄的 | 现算：把 `extended` 位形喂给同一套 FK，得 **0.685 m**（手抄值多算了 `gb_h` 20 mm，见 03 §8） |
| 画面能出，但相机水平线以下的面整批不见 + 剩下的一堆乱叠 | `toCam` 返回 `[右, 上, 深度]`，而近裁剪 `p[1]<0.05` 与画家算法的 `depth` 全把 `c[1]` 当**深度**用；另外 `-(d·f)` 的负号是 OpenGL 相机轴向的残留，在这套写法下让镜头前方的深度全为负 | 两套约定各自都"看起来对"，接在一起才炸。**投影约定必须写在函数旁边一次**，现在 `toCam` 上方就是 `[右, 深度, 上]` 的注释 |

> 三条合起来是一条更通用的话：**"这个文件存在"不等于"这个文件跑过"。**
> 一个从来没在浏览器里打开验证过的预览页，可以带着语法错活两周，
> 而所有人对它的印象都是"那是个能看模型的页面"。
